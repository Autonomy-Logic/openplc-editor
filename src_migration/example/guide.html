Documentação da migração

Como o exemplo está organizado

Um sistema pequeno de propósito: uma lista de variáveis PLC que se adiciona, renomeia, remove e salva. O tamanho é mínimo para que cada camada da arquitetura apareça com uma responsabilidade clara e um teste que a prova.

O código está em src_migration/example/ e é idêntico em openplc-web e openplc-editor. Ele não importa nada de src/ e não participa de nenhum build de produção. Serve de modelo para as features reais da migração.

A ideia central. A interface só mostra dados prontos e avisa o que o usuário quer fazer. Quem decide é a aplicação, com as regras do domínio. Estado e I/O ficam atrás de interfaces pequenas (ports), implementadas em camadas próprias. Uma única peça, a composição, conecta tudo.

O que o exemplo demonstra, em uma linha cada:

  • regras de negócio puras, testáveis sem React nem store (domain);
  • casos de uso que coordenam estado e I/O por ports (application);
  • Zustand encapsulado: só uma camada conhece a biblioteca (state);
  • controller sem React que entrega um modelo imutável e estável (presentation);
  • views controladas só por props, estilos fora do TSX (frontend, design-system);
  • a mesma view rodando com a lógica real ou com uma fixture simulada;
  • ciclo de vida explícito com dispose() e regras de import verificadas por teste.

Mapa das camadas

Cada seta significa “pode importar a entrada pública de”. O que não tem seta é proibido, e o teste de fronteiras falha. As dependências apontam para dentro: domínio e contratos não dependem de ninguém.

Três regras que explicam o desenho

  1. Contratos não dependem de nada. contracts/application e contracts/presentation só têm tipos. Assim, quem consome uma camada conhece apenas o contrato, nunca a implementação.
  2. Quem precisa declara; quem fornece implementa. A aplicação declara os ports de que precisa em application/ports. Estado e infraestrutura implementam esses ports. A aplicação nunca importa Zustand nem localStorage.
  3. Só a composição conhece tudo. Ela é o único lugar onde implementações concretas se encontram. Trocar localStorage por HTTP, ou o controller real por uma fixture, muda só a composição.

Camada por camada

Da mais interna para a mais externa. Para cada uma: o que faz, o que pode importar e o que nunca faz.

domain: as regras

Importa
nada fora de si mesma
Pacotes
nenhum

Dados imutáveis e funções puras. Uma edição recebe o documento atual e devolve o próximo documento ou a violação, sem lançar exceção e sem alterar a entrada. Quando nada muda, devolve o mesmo objeto, o que permite às camadas de cima evitar trabalho. 

export function addVariable(document, name, type): VariableRuleResult {
  const violation = checkName(document, name)
  if (violation) return { ok: false, violation }
  const variable = { id: document.nextId, name, type }
  return { ok: true, document: { variables: [...document.variables, variable], nextId: document.nextId + 1 } }
}

Nunca: React, store, I/O, textos para o usuário.

contracts/application e contracts/presentation: os acordos

Importa
nada
Conteúdo
só tipos

VariableListApi é a API pública da aplicação, usada por qualquer chamador (UI, atalho, ferramenta). VariableListModel e VariableListIntents são o que uma view recebe e o que ela pode pedir. ReadModel<T> é o formato observável que liga controllers a React. 

export interface ReadModel<T> {
  readonly getSnapshot: () => T                              // mesmo objeto enquanto nada mudar
  readonly subscribe: (listener: () => void) => Unsubscribe  // só avisa; quem lê chama getSnapshot de novo
}

Os membros são propriedades com funções, não métodos. Assim podem ser passados direto para um onClick sem perder o this.

application: os casos de uso

Importa
domain, contracts/application
Pacotes
nenhum

createVariableListService({ state, persistence }) recebe os ports por parâmetro e devolve a VariableListApi. É aqui que se decide quando uma edição é aceita, quando há uma operação em andamento (busy), como o save captura a revisão e o que fazer com respostas que chegam depois do dispose(). Erros do domínio são traduzidos para erros do contrato, para que nenhum chamador dependa de tipos do domínio.

Os ports ficam em application/ports. O port de estado tem métodos com significado (commitEdit, finishSave…) em vez de um setState genérico. Cada método é uma transação: documento, revisão e dirty nunca aparecem fora de sincronia.

Nunca: Zustand, localStorage, React, textos para o usuário.

state: o estado observável

Importa
application/ports, domain
Pacotes
zustand/vanilla (o único lugar)

Implementa VariableDocumentStatePort com uma store Zustand vanilla. A store em si nunca sai daqui: quem usa recebe só os métodos do port. Cada chamada da factory cria uma instância independente, então duas sessões nunca compartilham estado.

infrastructure: o I/O

Importa
application/ports, domain
Pacotes
nenhum (usa a Web Storage recebida por parâmetro)

Dois adapters do mesmo port. O de localStorage grava com um campo version e, ao ler, trata o JSON como unknown até validar cada campo; qualquer problema vira { ok: false }, sem exceção. O de memória serve aos testes e prova que a aplicação não sabe onde os dados moram.

Duas validações, dois donos. O adapter valida o formato (é um documento?). A aplicação valida o conteúdo com a regra do domínio (isConsistentDocument: ids únicos, nomes válidos e sem repetição).

presentation: o controller

Importa
contracts/application, contracts/presentation
Pacotes
nenhum (sem React, sem Zustand)

createVariableListController(api) combina o snapshot da aplicação com o estado local de formulário (rascunhos, mensagens) e produz um único VariableListModel. Textos de erro e de status são escritos aqui, em messages.ts.

Dois cuidados de desempenho que valem para todo controller:

  • o modelo só é recriado quando o snapshot ou o estado local mudou; senão, o mesmo objeto é devolvido;
  • linhas sem mudança mantêm a mesma referência, e a view usa memo para não re-renderizá-las.

design-system: a aparência

Importa
nada fora de si mesma
Pacotes
react; é a única camada que importa CSS

Tokens semânticos (--surface-panel, --action-primary, --status-error…) definidos em ThemeRoot, com valores claro, escuro e “system”. Primitivas (Button, TextField, SelectField, StatusMessage) com variantes tipadas e estilo em CSS Modules. Receitas (variableListRecipe) guardam o layout de um padrão composto, para que a view não tenha classes soltas.

Mudar a cor de um botão é editar um .module.css ou um token. Nenhum handler, controller ou caso de uso é tocado.

frontend: as views

Importa
contracts/presentation, design-system
Pacotes
react

VariableListView({ model, intents }) desenha o modelo e transforma eventos do DOM em intenções. Não guarda estado, não valida, não faz I/O e não sabe se as intenções vão para o controller real ou para uma fixture. A única conversão que faz é de string do <select> para um tipo que o próprio modelo ofereceu.

react-bindings: a cola com React

Importa
contracts/presentation, frontend
Pacotes
react

O Context carrega o controller, que é uma referência estável, e nunca o modelo, que muda. Cada componente assina só o que usa por useReadModel, que é um useSyncExternalStore sobre o ReadModel. 

export function ConnectedVariableList() {
  const controller = useVariableListController()
  const model = useReadModel(controller.model)
  return <VariableListView model={model} intents={controller} />
}

Views nunca importam bindings; bindings importam views.

fixtures: a simulação

Importa
contracts/presentation
Pacotes
nenhum

createVariableListFixture('empty' | 'populated' | 'loading' | 'save-failed') implementa o mesmo contrato do controller real, sem aplicação por trás. Registra as intenções recebidas e mostra textos que deixam claro que nada é gravado. Serve para revisar a interface antes de existir lógica e para testar views isoladas.

composition: a montagem

Importa
todas as entradas públicas
Pacotes
react, react-dom/client
export function createVariableListApp({ persistence }) {
  const state = createVariableDocumentStore()                          // de dentro para fora
  const service = createVariableListService({ state, persistence })
  const presenter = createVariableListController(service)
  return {
    api: service,
    controller: presenter,
    start: service.load,
    dispose: () => { presenter.dispose(); service.dispose() },        // de fora para dentro
  }
}

Factories simples, sem container de DI. createBrowserVariableListApp(storage) é a variante de plataforma com localStorage. browser-main.tsx cria a instância uma vez, fora do React, e monta VariableListRoot. Esse root aceita qualquer controller: o real ou uma fixture.

Fluxo de uma intenção: adicionar uma variável

Do clique até a tela atualizada, passando por todas as camadas:

  1. O usuário digita MotorSpeed. A view chama intents.changeNewName, e o controller guarda o rascunho no estado local e notifica. frontend/variable-list-view.tsx → presentation/variable-list-controller.ts
  2. O clique em “Add variable” chama intents.submitNew(). O controller remove espaços e chama api.addVariable({ name, type }). presentation/variable-list-controller.ts
  3. O serviço recusa se houver um load em andamento e aplica a regra do domínio addVariable ao documento atual. application/variable-list-service.ts → domain/variable-document.ts
  4. Se a regra recusar, o serviço traduz a violação para um VariableListError e o controller grava o texto do erro no estado local. O documento não muda. application → presentation/messages.ts
  5. Se aceitar, o serviço chama state.commitEdit(document). A store cria um novo estado com revision + 1 e notifica os assinantes. state/variable-document-store.ts
  6. O controller recebe a notificação, monta um novo modelo (reaproveitando as linhas antigas) e avisa React pelo ReadModel. presentation → react-bindings/use-read-model.ts
  7. useSyncExternalStore vê um snapshot diferente e re-renderiza. Só a linha nova renderiza; as outras são as mesmas referências. react-bindings/connected-variable-list.tsx → frontend

Um atalho de teclado, uma ferramenta de IA ou um teste chamariam o mesmo api.addVariable, com as mesmas regras e o mesmo resultado. Não existe caminho alternativo de escrita.

Save, revisões e dirty

Toda edição aceita gera uma nova revisão. O documento está sujo enquanto a revisão atual for diferente da última salva. O save captura o documento e a revisão antes do I/O:

Momento revision savedRevision dirty O que aconteceu
Carregou 1 1 não replaceLoaded instala o documento como já salvo
Adicionou Start 2 1 sim commitEdit
Clicou em Save 2 1 sim o serviço captura o documento da revisão 2 e marca saving
Adicionou Stop durante o save 3 1 sim edições continuam permitidas durante o save
Save terminou 3 2 sim finishSave(2): o que foi gravado é a revisão 2; Stop continua pendente

Outras garantias do mesmo fluxo, todas cobertas por teste:

  • save com falha não avança savedRevision e registra save-failed;
  • um segundo save enquanto o primeiro roda é recusado com busy;
  • adapter que lança exceção vira falha comum: a API pública nunca rejeita uma Promise;
  • resposta que chega depois do dispose() é ignorada e não altera nada.

Onde cada estado mora

Estado Dono Persistido
Variáveis e nextId port de estado (state), editado só pelos casos de uso sim, pelo port de persistência
Revisão, revisão salva, operação em andamento, última falha port de estado, na mesma transação do documento não
Rascunho do nome novo, rascunho de renomeação, mensagens estado local do controller (presentation) não
Foco, id de label (useId) primitivas do design-system não
Tema prop de ThemeRoot, escolhida pela composição não, neste exemplo

A regra prática: se um valor participa de save, undo ou navegação compartilhada, ele pertence à aplicação. Se é só para a tela, fica no controller. Se é só visual, fica na primitiva. As views não guardam estado.

Testes por camada

Cada camada é testada no seu próprio nível, com o mínimo de dependências. Os testes usam só a API comum a Vitest e Jest: sem vi nem jest, e sem matchers do jest-dom. Por isso os mesmos arquivos rodam nos dois repositórios.

Camada Arquivo Dublês O que prova
domain identifier.test.ts, variable-document.test.ts nenhum sintaxe IEC, nomes únicos ignorando maiúsculas, identidade preservada, invariantes
application variable-list-service.test.ts port de estado falso, persistência com Promises controladas edição durante save, falha de save, busy, load inválido, dispose
state variable-document-store.test.ts nenhum transações do port, revisão salva nunca volta, instâncias isoladas
presentation variable-list-controller.test.ts API falsa snapshot estável, linhas reaproveitadas, mensagens, renomear, unsubscribe e dispose
infrastructure persistence.test.ts storage em Map; Web Storage do jsdom ida e volta com versão, dados corrompidos viram falha, erros de storage não vazam
design-system components.test.tsx nenhum labels ligados, aria-invalid, variantes, tema
frontend variable-list-view.test.tsx modelo literal e intenções que registram chamadas a view mostra exatamente o modelo e transforma cada ação em uma intenção

Verificação de fronteiras

As regras de import moram em um só lugar, __architecture__/rules.ts. check-boundaries.ts lê cada arquivo com o pré-processador do TypeScript, que enxerga imports estáticos, de tipo, reexports, import() dinâmico e require, e compara com as regras. O teste roda o verificador sobre o código real e sobre exemplos sintéticos de violação.

  • entre camadas, só a entrada pública: ../domain pode, ../domain/variable não;
  • cada camada tem uma lista fechada de pacotes externos permitidos;
  • arquivo fora de qualquer camada falha, em vez de ser ignorado;
  • CSS só em design-system;
  • caminho que sai de src_migration/example falha, e @root também;
  • testes seguem a regra da própria camada e podem usar também fixtures e a Testing Library.

Exemplo de falha ao colocar export { createVariableDocumentStore } from '../state' em uma view:

{
  file: 'frontend/zz-negative-probe.ts',
  specifier: '../state',
  reason: 'frontend may not depend on state'
}

Mudar uma dependência permitida em rules.ts é uma decisão de arquitetura, para revisar como tal. Não é um ajuste para fazer o teste passar.

Como rodar

pnpm run example:dev        # página do exemplo em http://localhost:5190 (este guia: /guide.html)
pnpm run example:check      # typecheck + lint + prettier + testes (Vitest)
pnpm run example:arch       # só a verificação de fronteiras
pnpm run example:e2e        # Playwright contra a página do exemplo

openplc-editor

npm run example:check       # typecheck + lint + prettier + testes (Jest)
npm run example:arch

Conferir que os dois repositórios têm a mesma pasta

diff -r openplc-web/src_migration/example openplc-editor/src_migration/example

Criar uma feature nova seguindo o exemplo

  1. Domínio. Entidades e regras puras em domain, com resultado em vez de exceção. Testes sem React nem estado.
  2. Contrato da aplicação. Comandos, resultados, erros e snapshot em contracts/application, só com tipos.
  3. Casos de uso e ports. O serviço em application declara em application/ports o que precisa de estado e de I/O e traduz violações do domínio para erros do contrato. Testes com ports falsos.
  4. Implementações dos ports. Em state (Zustand fica só aqui) e infrastructure (HTTP, IPC, storage), com validação de tudo que entra.
  5. Contrato de apresentação e fixture. Modelo e intenções em contracts/presentation; fixture em fixtures para revisar a interface antes da lógica.
  6. View e design system. View em frontend usando só primitivas e receitas; estilos em .module.css com tokens.
  7. Controller. Em presentation, com snapshot estável e textos de mensagem. Testes com API falsa.
  8. Bindings e composição. Provider e componente conectado em react-bindings; factory e dispose() em composition.
  9. Fronteiras. Rodar example:arch (ou o equivalente da feature) e só então considerar a camada pronta.

Glossário

Port Interface declarada por quem precisa de algo (a aplicação), sem dizer como é feito.
Adapter Implementação concreta de um port: localStorage, memória, HTTP, IPC.
Snapshot Valor imutável do estado em um instante; o mesmo objeto enquanto nada mudar.
Read model Par getSnapshot + subscribe que expõe um snapshot observável.
Intenção Pedido emitido pela view (“adicionar”, “salvar”), sem retorno; o resultado volta pelo modelo.
Controller Objeto sem React que transforma o estado da aplicação em modelo de exibição e recebe intenções.
Fixture Implementação simulada de um contrato, usada em catálogo e testes; nunca toca recursos reais.
Composition root Único lugar que cria e conecta as implementações e controla o ciclo de vida delas.
Revisão Número que cresce a cada mudança confirmada do documento; base do dirty e do save.
Entrada pública O index.ts de uma camada; o único arquivo que outras camadas podem importar.
Guia do exemplo em src_migration/example. O código e os testes são a referência; atualize este guia na mesma mudança que alterar a estrutura.
